## 三、统一风险登记册（36 项发现去重合并后 24 项）

### 高危（7 项）

| # | 风险 | 影响的模块 | 证据 | 关联现象 |
|---|---|---|---|---|
| H1 | **上帝类耦合**：`RemoteDesktopSession` 约 3370 行同时承担 8 种 Controller 职责，任一子模块异常波及整条管线 | 引擎 | engine:1260-4628 | 连接成功画面异常/1FPS/黑屏/重连状态不一致等历史问题汇聚点 |
| H2 | **`stop()` 死代码**：全仓库无调用点（断开只走 start finally）→ 修饰键残留被控端、输入线程池/编码器/下载 task/采集器泄漏 | 引擎 | engine:4609-4628；cmdb_agent_core:905-915 | "UAC 后失控"、会话关闭后行为异常 |
| H3 | **多包帧单槽覆盖竞态**：一帧多 Annex-B 包（IDR 时 SPS/PPS 与切片分属不同 packet）逐个写入单槽 `_latest_frame_payload`，发送协程取走前被覆盖 → **SPS/PPS 静默丢失** → 观看端解码失败直至下一 IDR | 引擎发送侧 | engine:2112-2114, 4509-4521 | 疑似"12s 无 ack 回退 JPEG"兜底被触发的隐性根因 |
| H4 | **H264 seq 双重分配**：编码时 `_h264_results_from` 递增 `_h264_sent_seq` 写入 payload.seq（:3077），发送时 `_send_binary_frame` 又递增同一计数器生成 frame_id（:4546）→ inflight 被系统性虚高约一倍 → QoS 在真实积压一半时误降档 | 引擎 | engine:3077 vs 4546-4547, 3212/3220；A 路独立复核确认 | 画质自动变差类问题 |
| H5 | **三层超时互相打架 + 一次失败即杀 helper**：helper 内 input 8s/capture 12s，服务端管道客户端仅 5s——慢请求服务端先超时 → 重启健康 helper（无退避/熔断），helper 侧注入随后仍执行 → 输入迟到/重复；重启期间输入全回退本地 | 输入/助手 | session_manager:3203-3228 vs helper:1294/1240 | 84 号 VM"输入/帧反复中断"同型根因 |
| H6 | **`_restore_original_resolution` 永久悬挂窗口**：先置 `_resolution_restored=True` 无重试 + `ChangeDisplaySettingsW` 无超时 → finally 卡住、WS 永不关闭；半装显示驱动（VirtualDisplay install_pending）放大此风险 | 引擎 | engine:4600-4602, 1207, 1233, 1991 | 2213 事件循环卡死形态 |
| H7 | **虚拟显示 ensure 循环无失败熔断**：驱动永久装不上时（VMware 下 mm.inf 无法完成安装），服务维护线程以 ≥20s 节奏无限重试 8-10 个子进程/次（repair 有指数退避但 ensure 没有），且同步执行最坏阻塞管道线程 1-2 分钟 | 服务/虚拟显示 | session_manager:1434-1442; virtual_display_provider:292-313, 848-866 | 2213 日志刷屏 + 管道线程阻塞 |

## 四、三路交叉验证的重要结论

1. **"1 FPS / 黑屏"的成因已被三路审计共同锁定**：H7（虚拟显示 ensure 死循环，VMware 上 mm.inf 装不上）→ 显示基底判定 headless → 策略表返回空后端顺序 → blocker → 靠 mss/gdi 回退出帧（CPU 路径，帧率低）。
2. **"12s 无 ack 回退 JPEG"的隐性根因是 H3**（多包帧单槽覆盖竞态丢 SPS/PPS → 解码失败直到下一 IDR → 12s 内无 ack → 触发回退）——此前只知现象不知机制。
3. **"UAC 后失控"与 H2 直接相关**：会话断开后 stop() 不执行，修饰键残留 + 输入线程池悬挂。
4. **"画质自动变差"与 H4 相关**：inflight 虚高导致 QoS 误降档。
5. **84 号 VM"输入/帧反复中断"与 H5 同型**：超时不一致 + 无熔断的重启风暴。
6. ** base64 往返（M3）是最大的"白拿优化"**：本地进程内路径完全多余，去掉可同时降 CPU、内存峰值并缩小 H3 触发面。
7. **声明与行为漂移**（L1）需要系统性清理：能力面 note 说"local fallback disabled"，实际主路径就是本地直抓且回退默认开启——运维依据 capabilities 排障会被误导。

### P2 架构演进（子系统拆分，按 C 路草案）

按依赖方向单向拆分（依赖铁律：capture/codec/input/consent 不 import transport；transport 不 import session-manager；跨子系统只走 FrameSink/ControlSink trait + SessionContext 只读快照）：

```
rd-session-manager（生命周期状态机 Created→Consenting→Live→Restoring→Closed，强制顺序释放，修 R2/R4）
  ├─ rd-consent（per-session 实例 + 带超时 async request，修 M4）
  ├─ rd-capture（capture_loop + 基底修复整体迁出，异常降级为 error frame，修 M5）
  ├─ rd-codec（_h264_* 家族 + QOS_LEVELS，seq 单一 allotor，修 H4）
  ├─ rd-input / rd-files / rd-shell（现成边界物理移出）
  └─ rd-transport（三套中继统一 FrameTransport trait，审计/鉴权上移公共层，队列显式 maxlen，修 M6）
```

拆分顺序（风险从低到高）：① P0 三高危修复（不动架构）→ ② 抽 rd-codec（最独立）→ ③ 抽 rd-capture → ④ 合并传输层 → ⑤ session-manager 收口。每步保持 `remote_desktop_engine_v2.py` 为兼容门面，现有测试平滑迁移。

## 六、值得保留的设计亮点

1. **DesktopBinding 双签名 + generation + 校验矩阵**（助手模块）——"线程站在正确桌面上"的 Windows 难题工程化。
2. **capture/input 双 worker 隔离**——慢抓帧不阻塞注入（各自独立线程与队列）。
3. **8 后端采集注册表 + 基底策略表 + 失败分类 + 指数冷却**——全仓最精细的采集状态机。
4. **P0 全链路 stats**（FPS/RTT/ACK/Inflight/Input Latency，engine:3150-3191）——定位 H4 这类状态机问题的现成抓手。
5. **服务进程从不 SendInput**——输入全部收敛在目标会话进程内，SAS 走官方 sas.dll 通道，符合 Windows 会话隔离模型。
6. **兜底链完整**——12s 无 ack 回退 JPEG、编码失败 streak 处理、旧浏览器兼容、BT.709 色彩修正。
