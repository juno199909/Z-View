# 远程桌面修复改进计划（审计 × 实测分析 合并版）

> 日期：2026-09-17 ｜ 输入：《远程桌面核心六模块审计报告》（24 项风险）+ 用户独立分析（ACK 语义 / 串行流水线定量 / 媒体面状态机）
> 结论：**不推倒重写、不换语言**，按"架构收敛 + 链路测透"推进；传输按三阶段回归（WS+JPEG → WS+H264 → WT+H264）。

---

## 一、交叉验证：双方分析互相印证的结论

| # | 判断 | 用户分析 | 审计证据 | 交叉结论 |
|---|---|---|---|---|
| X1 | 1 FPS 不是网络差，是流水线被串行化 | Capture 25ms + Encode 20ms + Send 20ms ≈ 65ms ≈ 15FPS 封顶，再叠 GIL/CPU/解码 | A 路证实：grab 与 encode **await 串行**（engine:3272-3315），无流水线并行 | 成立。且抓帧/编码在 to_thread 而事件循环 await 其完成——帧预算被二者之和吃掉 |
| X2 | ACK 语义错误：decode() 返回 ≠ 已渲染 | frame_ack 更接近"包已交给 decoder"而非"画面已消费" | C 路证实：观看端 frame_ack 在 decoder.decode() 后立即发送；且 seq 双重分配（H4）使 inflight 虚高一倍 | 成立。背压信号应改为**渲染后确认**（requestVideoFrameCallback / output 计数） |
| X3 | 黑屏 = media plane 未就绪，control plane 成功 ≠ media plane 成功 | UI 过早 markSessionConnected()；SPS/PPS/profile/keyframe/首帧 IDR/分辨率变更 任一不一致 → Canvas 黑屏 | C 路证实：多包帧单槽覆盖竞态丢 SPS/PPS（H3）→ 解码失败直至下一 IDR | 成立。需引入**媒体面就绪状态**（首关键帧解码成功才标记视频就绪） |
| X4 | 分段指标缺失："又变 1 FPS"只能靠猜 | 应能直接看到 Capture FPS / Encode FPS / Queue / Send FPS / Network / Decode FPS / Render FPS 七段 | 审计：P0 stats 已有 sent/acked/inflight，但**无分段帧率与逐段耗时** | 成立。分段可观测是后续一切修复的前提，列为第一优先 |
| X5 | 架构方向：学习 RustDesk 的**职责划分**而非语言 | Session/Transport/Video 分离；不推倒重写 | C 路拆分草案（rd-session-manager/consent/capture/codec/transport + FrameSink trait）方向一致 | 采纳，作为 P2 架构演进蓝图 |

## 二、四条修复主线

### 主线 1：链路分段可观测（一切修复的前提）

目标：任意时刻能一眼看到七段指标，定位"Send FPS 2 ← 找这里"。

| 段 | 指标 | 落点 |
|---|---|---|
| Capture | capture_fps、grab_ms（EMA） | 引擎 capture_loop（已有部分，补齐结构化上报） |
| Encode | encode_fps、encode_ms、crf、scale、drops_backpressure | `_h264_stats` 已有，补分段口径 |
| Queue | queue_depth（单槽=0/1）、dropped_stale | `_enqueue_frame` |
| Send | send_fps、send_ms、inflight、bytes/s | `_send_binary_frame` |
| Network | ack_rate、rtt_ema、loss 估计 | 观看端 frame_ack（语义修正后） |
| Decode | decode_fps、decode_ms | 观看端 decoder.decode 计时 |
| Render | render_fps、canvas 递交间隔 | 观看端 requestVideoFrameCallback |

- 载体：复用 P0 stats 管道（engine:3150-3191），每 2s 汇总一帧 JSON `pipeline_stats`；观看端在状态栏展开七段显示。
- 验收：人为在网关限速/加压，七段中掉段的环节一眼可见。

### 主线 2：流水线正确性

| # | 任务 | 对应风险 | 要点 |
|---|---|---|---|
| 2.1 | **ACK 语义修正**：区分"已提交解码"与"已渲染"两级确认；背压改为以渲染确认（requestVideoFrameCallback 计数）驱动 inflight | X2/H4 | 观看端解码后立即 ack 改为渲染回调 ack；或保留双 ack（decode-ack 用于去重、render-ack 用于背压） |
| 2.2 | **seq 单一分配点**：删除 `_h264_results_from` 的递增，统一发送侧分配 | H4/A#2 | engine:3077 vs 4546-4547 |
| 2.3 | **整帧队列**：同一帧的多 Annex-B 包合并为一个入队单元（或队列改整帧语义），杜绝 SPS/PPS 被单槽覆盖 | H3 | engine:2112-2114, 4509-4521 |
| 2.4 | **抓帧/编码解耦**：抓帧与编码拆为两个异步阶段（帧队列缓冲 ≥2 帧编码深度），帧率 = max(grab, encode) 而非 1/(grab+encode) | X1/M2 | 需内存上限（≤4 帧）防积压 |
| 2.5 | 本地路径去 base64 往返（帧队列改二进制直传） | M3 | engine:3080, 4543 |

### 主线 3：媒体面状态机（黑屏治理）

| # | 任务 | 要点 |
|---|---|---|
| 3.1 | **连接状态拆分**：`control: connected` 与 `media: waiting_keyframe / decoding / playing` 分离上报；UI 在 media 未就绪时显示"正在解码视频流…"而非"已连接" | X3 |
| 3.2 | **H264 配置一致性自检**：首帧必须 IDR（解码器 configure 后首个 chunk 前 force_keyframe——引擎已有 `_h264_keyframe_requested`，确认覆盖"编码器重建后首帧"场景）；SPS/PPS 与切片同帧；分辨率变更 → 编码器重建 + 强制 IDR + 观看端 reconfigure 的顺序保证 | X3/H3 |
| 3.3 | **解码失败可视化**：观看端 decode 失败计数上报，连续失败触发引擎 force_keyframe（现有机制确认覆盖） | H3 |

### 主线 4：边界收敛（架构演进，审计 P2 蓝图）

按依赖铁律（capture/codec/input/consent 不 import transport）分五步拆分，每步保持 `remote_desktop_engine_v2.py` 为兼容门面：
① P0 高危修复（不动架构）→ ② 抽 rd-codec → ③ 抽 rd-capture → ④ 合并三套传输（审计/鉴权上移公共层、队列显式 maxlen）→ ⑤ session-manager 收口（状态机 Created→Consenting→Live→Restoring→Closed + 强制顺序释放，修 stop 死代码/分辨率恢复悬挂）。

## 四、红线与原则（固定不变）

1. 不推倒重写、不换语言（RustDesk 学边界不学语言）
2. Control Plane / Data Plane 分离：Session Manager 不感知视频细节
3. 每层自带 metrics/logs/timeout/state/fallback
4. 每步保持 engine 兼容门面 + 测试平滑迁移
5. 先测透再上：每阶段有 soak 验收才算完成
