# Z-View 终端网络流量监控需求

## 1. 功能名称

**终端网络流量监控（Endpoint Network Traffic Monitoring）**

## 2. 功能目标

在 Z-View Agent 中增加网络流量采集能力，用于监控 Windows 终端的网络连接状态、上传/下载流量、实时上传/下载速度以及基础网络质量。

该功能必须以**低资源占用**为第一原则。

第一阶段仅采集**网卡级别的网络统计数据**，禁止通过抓包、网络内容解析或 DPI 等高负载方式实现。

---

# 3. 产品定位

该功能属于：

> **Z-View → 终端管理 → 网络状态**

用于帮助 IT 管理员快速判断：

* 终端是否正常联网
* 当前使用哪张网卡
* 当前上传/下载速度
* 网络流量是否异常
* 终端网络质量是否正常

该功能不是网络流量分析系统，不要求实现类似 Wireshark、Ntop 或专业 NDR 产品的能力。

---

# 4. 第一阶段功能范围

## 4.1 网卡信息

Agent 应能够获取 Windows 终端当前网络接口信息：

* 网卡名称
* 网卡描述
* 网卡类型

  * Ethernet
  * Wi-Fi
  * VPN
  * Virtual
  * Other
* 网卡 MAC 地址
* IPv4 地址
* IPv6 地址
* 默认网关
* DNS
* 网卡连接状态
* Link Speed

需要支持多网卡。

例如：

```text
Ethernet
状态：Connected
MAC：XX-XX-XX-XX-XX-XX
IPv4：192.168.10.125
Gateway：192.168.10.1
Speed：1 Gbps

Wi-Fi
状态：Disconnected
IPv4：-
Speed：-
```

---

# 5. 网络流量统计

## 5.1 必须采集

对于每个有效网络接口采集：

* RX Bytes：累计接收字节数
* TX Bytes：累计发送字节数
* RX Packets：累计接收数据包
* TX Packets：累计发送数据包
* RX Errors
* TX Errors
* RX Drops
* TX Drops

如果 Windows 对某些指标无法稳定获取，则允许标记为 unavailable，不允许伪造数据。

---

# 6. 实时上传/下载速度

Agent 不应直接依赖系统提供的“当前速度”，而应通过累计字节数计算。

计算公式：

```text
download_bytes = current_rx_bytes - previous_rx_bytes
upload_bytes   = current_tx_bytes - previous_tx_bytes

download_speed = download_bytes / elapsed_seconds
upload_speed   = upload_bytes / elapsed_seconds
```

需要考虑：

* Agent 重启
* 网卡重启
* 网卡切换
* 系统计数器归零
* 计数器异常回退

如果：

```text
current_bytes < previous_bytes
```

则认为计数器发生重置，应重新建立基线，不得产生巨大的负数或异常流量。

---

# 7. 采集频率

默认：

```text
Network Collector Interval = 10 seconds
```

允许配置：

```text
5s / 10s / 30s / 60s
```

默认使用：

```text
10 seconds
```

不得默认使用 1 秒级持续高频采集。

---

# 8. 上报策略

Agent 本地可以每 5～10 秒计算一次实时速率，但不要求每次都写数据库。

建议：

```text
Agent
 │
 ├── 每 10 秒读取系统网络计数器
 │
 ├── 计算 RX/TX Rate
 │
 ├── 更新本地网络状态
 │
 └── 周期性上报平台
          │
          └── Z-View Backend
```

平台侧：

### 实时页面

通过现有 WebSocket / 实时通信机制提供实时网络状态。

### 历史数据

第一阶段建议按照：

```text
1分钟
```

粒度保存网络统计数据。

不允许每 5～10 秒直接写 MySQL。

# 12. 网络质量监控

第一阶段可以同步提供基础网络质量检测。

Agent 定期测试：

* Default Gateway RTT
* DNS RTT
* Internet RTT
* Packet Loss

例如：

```text
网络质量

Gateway RTT      2 ms
Internet RTT    38 ms
Packet Loss      0.0%
DNS Response      8 ms
```

网络质量测试必须采用轻量级请求，不得使用持续 ICMP Flood 或高频探测。

默认：

```text
网络质量检测：30～60 秒
```

---

# 13. 异常检测

第一阶段实现简单规则即可。

例如：

### 网络断开

```text
interface.status = down
```

产生：

```text
Network Interface Down
```

### 流量异常

例如管理员配置：

```text
Download > 100 MB/s 持续 5 分钟
```

产生：

```text
High Network Traffic
```

### 丢包异常

例如：

```text
Packet Loss > 10%
持续 3 次
```

产生：

```text
Network Quality Degraded
```

### 网络质量恢复

异常恢复后生成 Recovery Event。

---

# 14. 资源占用要求

这是本功能的核心要求。

网络采集模块必须：

* 不抓包
* 不做 DPI
* 不解析网络内容
* 不扫描所有 TCP 数据
* 不持续读取网络数据包
* 不创建高频线程
* 不进行高频数据库写入

优先使用 Windows 系统提供的：

* Network Interface counters
* Performance Counter
* IP Helper API
* Windows 网络接口 API

读取系统累计计数器并进行差值计算。

---

# 15. Agent 资源限制

目标：

### CPU

正常采集期间：

```text
平均 CPU 增量 < 0.5%
```

短时间读取网络信息允许出现瞬时波动。

### 内存

网络采集模块：

```text
额外内存 < 20 MB
```

目标控制在：

```text
< 10 MB
```

### 网络流量

采集模块自身产生的网络开销必须尽可能低。

不得因为监控网络流量而产生明显的额外网络流量。

---

# 17. 数据采集与业务解耦

推荐：

```text
NetworkCollector
       ↓
NetworkSnapshot
       ↓
Agent Runtime
       ↓
Heartbeat / Report
       ↓
FastAPI
       ↓
Network Service
       ↓
Database
```

不要让 NetworkCollector 直接操作 MySQL。

Agent 只负责：

> 采集 → 计算 → 上报

Backend 负责：

> 接收 → 存储 → 聚合 → 查询 → 告警

Frontend 负责：

> 展示 → 图表 → 查询 → 交互

---

# 18. 多网卡处理

必须支持：

```text
Ethernet
Wi-Fi
VPN
Virtual Ethernet
Hyper-V
VMware
Docker
```

但前端默认只突出显示：

```text
当前活跃物理网络接口
```

虚拟网卡可以作为高级信息展示。

需要避免：

* Docker 虚拟网卡导致流量重复计算
* VPN 虚拟接口与物理接口产生误导
* Loopback 被错误统计
* Windows 虚拟交换机导致重复统计

---

# 19. 安全要求

网络监控模块：

* 不读取用户网络内容
* 不保存 HTTP/HTTPS 内容
* 不保存 URL 内容
* 不保存密码
* 不保存数据包 Payload
* 不执行网络嗅探
* 不修改网络配置

只采集：

> 网络接口元数据 + 系统累计流量统计 + 网络质量指标

所有网络监控数据必须遵循现有 Z-View RBAC 和审计机制。

---

# 20. 第一阶段明确不实现

以下功能暂时不要实现：

* ❌ DPI
* ❌ 数据包抓取
* ❌ HTTP 内容分析
* ❌ HTTPS 解密
* ❌ DNS 全量记录
* ❌ 进程级流量统计
* ❌ 每个连接的详细流量统计
* ❌ 网络入侵检测
* ❌ 网络行为分析
* ❌ 流量内容审计

这些属于后续高级网络分析能力，不属于当前 Z-View 核心范围。

# 22. 验收标准

## 功能验收

至少满足：

* [ ] 正确发现 Windows 网卡
* [ ] 正确获取 IP/MAC
* [ ] 正确识别网卡状态
* [ ] 正确获取 RX/TX Bytes
* [ ] 正确计算上传速度
* [ ] 正确计算下载速度
* [ ] 支持多网卡
* [ ] 支持网卡计数器重置
* [ ] 支持 Agent 重启后重新建立基线
* [ ] Backend 可以接收网络数据
* [ ] Frontend 可以查看网络状态
* [ ] 可以显示实时上传/下载速度
* [ ] 可以显示历史流量趋势
* [ ] 可以检测网络断开
* [ ] 可以检测基础网络质量

## 性能验收

在正常 Windows 终端上：

```text
CPU 平均额外占用 < 0.5%
Memory 额外占用 < 20 MB
```

并验证：

* 连续运行 24 小时无内存泄漏
* 网络断开/恢复不会导致 Agent 异常
* 网卡启停不会导致异常流量数据
* Agent 重启不会产生异常流量峰值
* 多网卡环境数据不会重复计算

# 23. 实施原则

开发过程中必须遵循：

1. **先复用现有 Agent 架构**
2. **不新增独立 Network Agent**
3. **不抓包**
4. **不引入高负载网络监控框架**
5. **不改变现有 Heartbeat 协议的核心行为**
6. **网络采集模块必须独立封装**
7. **采集、计算、上报、存储分离**
8. **默认低频采集**
9. **所有异常情况必须 Fail-safe**
10. **必须提供单元测试**
11. **必须提供 Windows 实机测试**
12. **不得因为增加网络监控导致现有 Remote Desktop 性能下降**

---

# 24. 特别要求：不能影响远程桌面

Z-View 当前 Remote Desktop 属于核心功能。

因此新增 NetworkCollector 时必须特别验证：

```text
NetworkCollector
        ↓
CPU / Memory / Network
        ↓
不能明显影响
        ↓
Remote Desktop
```

尤其需要测试：

* H.264 编码
* WebTransport / QUIC
* WebSocket
* Input latency
* Frame FPS
* Agent heartbeat

在远程桌面运行期间开启网络监控，不得导致明显的 FPS 下降或输入延迟增加。
